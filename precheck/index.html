Findings

  1. 1. precheck (like team mr) is still answered after RUN COMPLETE. handle() refuses on a pause, a removal, a stall and when the time is up, but nothing checks state/DONE. After a real RUN COMPLETE, team precheck ran the checks (990 ms) and --quick passed (62 ms); on page 1 the same happened in the live run. team-choice.md and design.md promise refusal 'whenever the door is (pause, removal, time up)', which is what the code does, so this is consistent; but the run is over and the runbook tells agents they may stop. The dev run shows the same for team mr: w1's merge was accepted at minute 36.4, three minutes after RUN COMPLETE. template/harness/gateway.py:571-590
  2. 2. The team's evidence: the conflicts were real, but cheap for the merge job. 11 of 27 merge requests in the dev run were rejected for conflicts, more than the four the document lists. Each was answered within about 0.2 s of getting the lock, so they cost the merge job almost nothing. What they cost was waiting: 713 s in the queue behind other merges' checks before hearing 'conflict', which team precheck --quick answers in well under a second without the queue. The document's agent-side costs (~40 s to 1 min of local checks per round) are not in the records and are not verified here. Its '45 minutes' is wrong (14.7). references/decisions/team-choice.md
  3. 3. Observation: a refused precheck is logged without '--quick'. Door refusals return the bare op as the log's detail, so both of h2's paused requests read 'precheck' though one was --quick. Harmless, but the record cannot tell them apart. template/harness/gateway.py:573-582
  4. 4. Observation: no live agent has used it yet. In page 1's run (2.9 minutes, no rejected merge, no shared file) no agent ran team precheck. The briefs suggest it 'when your work touches files others change'; a task with shared files is needed to see whether agents use it. template/docs/helper.md:23
