How the pieces connect

The check runs in bubblewrap with no network, so it can only judge the evidence the agents commit. Whether that evidence is true is answered by the boss's read-back, which goes to S3DF over a bridge no agent used and shares no code with the check.

Findings

  1. Claude Code's classifier refused the first bridge call, so a remote task's authorization has to reach the brief. At 23:06:39 h2 ran bridge --session tat-s3df-04 status, auto mode denied it as "Unauthorized Access", and harness/denied.py paused the team, as designed. The permission to use a bridge was only in STATEMENTS.md, a repo file. The classifier judges actions against the user's request, and the brief is the agent's first user message (references/claude-code.md:57). After the boss typed the owner's authorization into each window as a user message, no bridge call was refused again: the run has exactly one blocked action. Suggested fix: a task-level authorization field in config.json that harness/render.py puts into every brief. Not verified that this alone avoids the pause.
  2. The merge check can't see S3DF, so a well-formed fake value passes it. The check runs with no network (run_check, harness/gateway.py:352). It caught 9 of 9 malformed or wrong-host files, but a sha256 of 64 zeros passed. For remote work, the read-back over an independent bridge is the real verification, and this run needed it to call the work done.
  3. Bridge access isn't governed by profiles. Every agent had the sealed profile, with no shell_net, yet reached S3DF. bridge is a local socket client, not one of the network commands the monitor knows (profiles.NET_CMDS). With the sandbox off, any agent could also use any session under ~/.bridge/. "Own bridge only" held here because of the instructions, and the action log shows each helper's commands named only its own session. Nothing enforced it.
  4. An agent wrote outside its workspace. h1 saved a remote output to /tmp/claude-1000/c.txt before parsing it (offline monitor, 23:07:41). That's allowed in an unwalled run and harmless here. It shows the workspace boundary is only requested.

Not covered

  • Slurm jobs (salloc, srun). Ruled out on purpose, to stay clear of the account's node limit.
  • Large transfers. Everything moved was under 1 KB.
  • A bridge session dying mid-run. All four stayed up for the whole run.
  • A walled run (sandbox on). references/claude-code.md records that bridge fails on its Unix socket there. Not retried.
  • The lead doing remote work. It coordinated and made no bridge calls.
  • Runs longer than a few minutes, and more than two helpers.
